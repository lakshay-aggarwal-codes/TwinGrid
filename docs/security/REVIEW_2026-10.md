# Security and dependency review, October 2026 (Task 27 / SEC-002)

**What this is.** A code-and-configuration review plus repeatable probes written as tests (`tests/api/test_sec002_probes.py`,
58 cases) that call the real app over HTTP in-process with an in-memory SQLite database. **It is not a penetration
test.** Nothing was run against a deployed host, a real mail provider, Postgres, Redis, or a browser.

**Tree reviewed.** The uploaded `TwinGrid-main.zip` (no git history). Tasks 22 and 25 (the playbook's prerequisites) and
Tasks 11, 20, 21, 23, 24, 26 are **not applied in that tree**, so the visitor UI, the admin-console front end and CI
workflow changes from those tasks were not reviewed. Re-run `pytest tests/api/test_sec002_probes.py` after they land.

## What was probed and what held

All of these are tests; a probe was checked to be able to fail by temporarily weakening the code (HS512 accepted, a demo
write route allow-listed, the per-email limit removed) and confirming a failure, then restoring it.

**Access requests** (`/api/access-requests*`, admin queue)
- Mass assignment: `role`, `status`, `id`, `user_id`, `decided_by`, `is_admin` in the submit body never reach the row; activation creates a `viewer` and ignores `role`/`username`; decision bodies reject unknown fields (422).
- Enumeration: an existing account and a new address get the same status, keys, message and token lengths; the decoy polls as `pending`; unknown reference, wrong token and missing token give byte-identical 404 bodies; resend answers identically for known, wrong-token, unknown and empty. Timing: see M2.
- Replay and confusion: an activation token works once, and the replay body equals the garbage-token body; a status token cannot activate and an activation token cannot read status.
- Input: 2 MB body gives 413; 200 000-deep JSON, `null`, `[]`, wrong types, a 5 000-character address and an 81-character name give 413/422 with no 500; CR/LF/NUL/space in the address are refused (header injection); HTML and spreadsheet-formula text is stored verbatim and returned only as `application/json` with `nosniff` (escaping is the mail layer's and the UI's job; the mail layer is covered by `tests/test_notify_mail.py`). There is no CSV export of requests.
- Rate limits: the per-IP submit limit holds and ignores `X-Forwarded-For` by default; with `TRUST_PROXY_HEADERS=true` and one hop, spoofed left-hand entries do not dodge it; the per-address limit holds across IPs; the demo-session and activation-guessing limits hold.
- Authorisation: every admin-queue route is 401 anonymous, 403 viewer and operator.
- Logs: over submit, approve, a failed and a successful activation and a status poll, no activation token, status token, password or client IP appears in any log record, including driver logs at DEBUG.

**Tokens and demo sessions**
- Forged tokens (`alg: none`, HS512 with the right key, wrong key, no `exp`, expired, no `sub`) for a real admin id are all 401. A `role: admin` claim in a validly signed token does not override the database role (403).
- A demo token is refused every write with `demo_read_only` (including a route that does not exist yet, which proves the middleware rather than the route), trailing-slash, double-slash, encoded and upper-case path variants never return 2xx, a lower-case `bearer` scheme works the same, it cannot be refreshed or used on the admin queue, and it is not accepted from a query string or cookie. Its lifetime is at most 30 minutes.

**Copilot** (`/api/copilot/ask`): needs a token; prompt-injection, SQL, template and script strings give a normal 200 with no secret, no address and no template evaluation in the answer; 501-character questions and unknown body fields give 422; a non-numeric alert id gives 404; it has no write side effect.

**WebSocket** (`/ws/live`): a ticket is single-use; expired, unknown, oversized and missing tickets are refused (4001); a bad ticket is never retried as a token; `WS_ALLOW_QUERY_TOKEN=false` closes the query-token path while tickets keep working; with `WS_ALLOWED_ORIGINS` set a foreign or `null` origin is refused (4004). Cross-user is by construction: a ticket stores the user it was issued for and redeeming returns that user; it cannot be changed by the redeemer.

**Headers and CORS**: `nosniff` is present; a foreign origin receives neither `*` nor its own origin in `Access-Control-Allow-Origin`, on a normal request or a preflight.

## Open items and what to do about them

**M1, WebSocket defaults in production.** Set `WS_ALLOW_QUERY_TOKEN=false` (needs `REDIS_URL`; startup rule R13 already enforces that pairing) and set `WS_ALLOWED_ORIGINS` to the deployed front-end origin. Redis is also needed whenever more than one API process runs, because the memory ticket store is per process. I did not change the defaults: a rule that fails production start-up could take a working deployment down and belongs with the Task 21 deployment review.

**L2, proxy and rate-limit keying.** Behind Railway or any proxy set `TRUST_PROXY_HEADERS=true` and `TRUSTED_PROXY_HOPS` to the real number of proxies in front of the app (take the right-most entries, which is how the code reads them). Without it every visitor shares the proxy's address and the 5 submissions per hour limit becomes global. Run one API worker, or move limits to Redis, before relying on the numbers. Not verified here: the actual hop count on Railway.

**L3, L4, L5** are accepted as described; L5 does not occur with the Postgres driver as far as this review could tell, but that was not tested.

**CORS and the CSP origin.** `netlify.toml` pins the API origin (`function-bun-production-6ce5.up.railway.app`) in `connect-src`. That is deliberate and commented in the file; it is a coupling, not a vulnerability. If the API host changes, the front end will silently fail to connect until the CSP is edited.

## Dependencies

`pip-audit --requirement requirements.lock --require-hashes --disable-pip --strict` found 12 advisories in 4 packages; after the upgrades 3 remain (waived). `npm audit` found 11 (6 high); after `vite` 7.3.7, 10 remain (5 high), all waived. Both audits query live databases, so the numbers change over time. `requirements.lock` hashes for the two upgraded packages are the SHA-256 values PyPI publishes for every file of that release; they were not independently recomputed from downloaded files. The lock does not include `torch`'s CUDA dependencies by design, so a full `--require-hashes` install of the whole lock was not possible here; the other 91 pinned packages were installed with their hashes and the backend suites run on them. TensorFlow and PyTorch themselves were not installed.

## Secret scan

`gitleaks dir . --config .gitleaks.toml` (gitleaks 8.30.0, working tree only, **not** git history, which this tree does not have) found 7 matches, all made-up strings inside tests; they are now allowlisted with a comment saying why. It found no real credentials. A log file my own test runs created in the sandbox contained test JWTs; it is git-ignored, was deleted, and is not part of the delivered tree.
