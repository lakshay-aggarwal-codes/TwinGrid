# Model Card: Thermal Forecaster (LSTM)

## Intended use
Forecasts server outlet/thermal telemetry `horizon` steps ahead (default 6
steps = 30 min at 5-min intervals) from a `seq_len`-step (default 12 = 1h)
window of recent sensor history. Used by the dashboard's forecast display;
not used for safety-critical control decisions (PPO/rule-based cooling
control act on current state, not this forecast).

## Training data
`data/raw/sensor_data.csv` — 90 days synthetic data from
`src.data_generator.generate_sensor_data(days=90, seed=42)`, itself driven
by `DigitalTwin`'s physics (see `src/digital_twin.py`). Not real facility
data — see `docs/model_cards/LIMITATIONS.md`.

## Split
Chronological 80/20 (`DataPipeline(train_ratio=0.8)`) — train on the first
80% of days, test on the last 20%. Not a random split: prevents the model
from training on data that's chronologically after its test window.

## Metrics (reported by `notebooks/train_all.py`, held-out test set)
See `models/registry.json` for the actual numbers from the most recent
training run (`log_model("forecaster", ...)`). As of this writing that file
reflects RMSE/MAE in °C on the held-out split.

## Known limitations
- Trained entirely on synthetic data generated by the same physics model
  the rest of the system uses — metrics measure how well the LSTM fits
  `DigitalTwin`'s own simulated thermal dynamics, not real hardware
  behavior. See `docs/model_cards/LIMITATIONS.md` for the shared caveat.
- No held-out *drought* scenario in the forecaster's own training/eval
  split specifically — drought/water-stress dynamics are tested via the
  PPO optimizer's `compare_scenarios`, not this model's own eval.
