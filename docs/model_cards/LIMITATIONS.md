# Shared limitations of every model in this system

Read this before quoting any model number. Per-model detail is in `forecaster.md`, `anomaly_detector.md` and
`ppo_optimizer.md`; each number in those cards is an `EVIDENCE` line that points at the file it came from.

## 1. Synthetic training data (applies to all three models)
Every model in this system (forecaster, anomaly detector, PPO optimizer) is trained on data generated by
`src.data_generator`/`DigitalTwin` itself — the same physics model the product simulates, not measurements from a
real facility. This means:

- Metrics (F1, RMSE, PUE improvement) measure how well each model fits the simulator's own physics/patterns, not real-world generalization.
- Any systematic gap between the simulator and a real facility (thermal time constants, sensor noise characteristics, failure
  modes) is invisible to these numbers by construction.
- Real historical data-centre datasets (public PUE benchmarks, or a partner facility) are needed to calibrate the physics and
  validate these models against reality, not just internal consistency.

Report these metrics as "performance on the current simulator," not as a claim about real-facility performance, until real data closes this gap.

## 2. What is unevaluated or negative today
| Model | Plain statement |
|---|---|

| Anomaly detector | The headline F1 used a threshold tuned on the rows it is scored on. The event-level evaluation exists as code and config but has no result on file. |

| PPO, five v2 candidates | Scored once under the physics-1 protocol: outcome `C`, claim allowed: none. A fixed setting scored higher than every seed. Not promoted. |

## 3. Things that hold for the whole system
- **Carbon is an assumption.** No carbon data file ships; the twin uses a flat assumed intensity, labelled as such
  (`docs/model_cards/DATA_TRUTH.md`). Carbon figures and anything optimised against them are not grid measurements.
- **Physics versions differ.** The promoted forecaster and anomaly detector, and the legacy PPO, were trained under physics
  `legacy-0` whose parameters were not recorded; the v2 PPO candidates use physics `1`. Two registry entries still carry a
  named compatibility waiver, and no re-validation record is on file.
- **The rule baseline is weak.** In both runs a fixed setting beat it on reward and water, so "better than the rule baseline" is
  a low bar. In the older legacy-physics run no policy kept the inlet temperature above its simulated minimum; under physics 1
  the hard-limit counters are zero for the rule, the best constant and every PPO seed.
- **Simulated, lumped, uncalibrated.** The model is a lumped thermal and energy simulator with published parameters, not fitted
  to any facility (`docs/PHYSICS_V2.md`). Nothing here is a measurement.
- **No uncertainty is shipped.** Sample sizes are small (3 seeds for the legacy PPO, one run for the other two) and the
  stated interval for the legacy PPO uses a multiplier that is too small for 3 seeds.
- **Not reproducible from this repository alone.** The training data file is not shipped; the registry holds its SHA-256, not
  the data.

## 4. Wording rules for the UI, README and slides
Allowed: "simulated", "simulator result", "synthetic-data result", "not evaluated", "candidate". At most, and only after a
passing decision gate: "simulator-validated candidate" (the pre-registration's own limit).
Not allowed without new evidence: "AI-optimized", "accurate", "validated" (without "simulator"), "predicts failures",
"real-time optimisation", "production-ready", any saving or accuracy claim about a real facility.
