# RT-001: Telemetry / history reality check

Status: **PARTIAL.** Source-level findings only. Nothing below was run on a live stack: the build sandbox has no Docker, Postgres or backend dependencies (`import fastapi` fails) and no network. Every runtime item is marked `blocked` with the exact PowerShell command. ADRs 004 to 007 were not re-litigated.

Evidence labels: **source** = read in the uploaded tree; **runtime** = observed on a running stack (none yet).

## Findings

| # | Question | Status | Evidence |
|---|---|---|---|
| 1 | Does the simulator write stored telemetry? | resolved with evidence (source) | `api/services/live_broadcast_service.py` `_store_live_sample` calls `ingest_samples(..., stream_id="live", origin="simulated")` every tick when `config.telemetry_store_enabled()`; default is `true` (`api/config.py`, `docker-compose.yml`, `.env.example`). `BROADCAST_INTERVAL_SECONDS = 3`. If the five feature sensors are not seeded, every sample is rejected as `unknown_sensor` and the tick falls back to one legacy `sensor_readings` row, so the history endpoints return `items: []` until `scripts/seed_facility.py --seed-sensors` has run. `STATUS.md` called this a producer gap: stale, fixed. Runtime growth: **blocked** (#7). |
| 2 | Duplicates (same sensor + ts) | resolved with evidence (source) | Unique constraint `uq_telemetry_sensor_stream_event` on `(sensor_id, stream_id, ts_event)` (`models/db_models.py`); `ingest.py` uses `ON CONFLICT DO NOTHING`, then counts `duplicate` (same value) or `conflict` (different value, first write wins). Runtime duplicate count: **blocked** (#7). |
| 3 | Units | resolved with evidence (source) | `validation.py` rule 3 rejects a sample whose `unit` differs from the sensor's (`unit_mismatch`, no conversion). The live writer sends no `unit`, so the sensor's seeded unit applies. |
| 4 | Ordering | resolved with evidence (source) | API order is keyset `(ts_event, id)` ascending; the frontend must not re-sort (G-HIST.md). |
| 5 | Gap behaviour vs the live tick | **open, needs Task 23 decision** | Seeded sensors declare `sampling_interval_s = 300` (`scripts/seed_facility.py`, "one twin step"); `/gaps` reports a gap only when consecutive valid samples are more than 1.5 x that interval apart (`telemetry_routes.py`, `GAP_FACTOR`), i.e. over 450 s. The live loop writes about one sample per 3 s. A dropped-frame outage shorter than 450 s will therefore never appear in `/gaps`. Task 23's own gap detection uses the feed's `seq` / `ts_ingest` instead (`backfill.ts`), so it is not affected, but the history page's gap markers are coarse. Status: intentionally unsupported for short gaps (UX text needed: "gaps shorter than 7.5 min are not shown"). |
| 6 | Restart / sequence regression | resolved with evidence (source) | Server `_tick_seq` restarts at 1 with the process. `telemetry/feedStore.ts` treats `s < last` as a restart (state reset, `restartCount + 1`), `s === last` as a duplicate, a missing `seq` as unordered. `backfill.ts` does not backfill across a restart or a frame without `seq`/`ts_ingest`. After a restart the stored stream continues by wall-clock `ts_event`, so history is unaffected. Runtime restart check: **blocked** (#7). |
| 7 | Real stack measurements (10 min growth, per-sensor counts, ordering, UI page, curl, restart) | blocked | Needs Docker Desktop. Commands below. |
| 8 | Does any chart consume backfilled samples? | resolved with evidence (source): **no** | `createBackfiller` fetches samples per measurand (`backfill.ts`) and keeps them in `BackfillState.series`. The only consumers are `backfillState.ts` -> `StatusBar.tsx` via `backfillLine` (a text line with the recovered count). `components/charts/HistoryView.tsx` builds from `useTelemetryHistory`, not from backfill; no live chart reads `series`. Task 23 must wire the samples in. |
| 9 | Thermal-mode rack rendering | resolved with evidence (source); owner decision unrecorded | `three/Rack.tsx` renders two stacked halves in thermal mode (`thermalColors.inlet` lower, `.outlet` upper), or one `WAITING_COLOR` box before a live reading. `three/thermalMapping.ts` documents that the backend has one facility-wide inlet/outlet pair, applied identically to every rack; `three/readout.test.ts` covers it. The decision itself is not recorded anywhere: status `blocked` on the owner, one line to add to `STATUS.md` once decided. Not run in a browser. |
| 10 | UQ-1 to UQ-4 | resolved with evidence | ADR 004 (utilisation is a fraction), 005 (rack id parity, `tests/test_ig05_rack_id_parity.py`), 006 (alert write path), 007 (`/api/simulate` persistence). `STATUS.md` still listed them as unrecorded: stale, fixed. |

## Runtime checks (not run). PowerShell, from the repo root

```powershell
# Start the demo stack (Docker Desktop required); good result: URLs and demo logins printed
.\scripts\demo.ps1

# Confirm the five feature sensors are seeded; good result: 5 rows
docker compose --env-file .env.demo -f docker-compose.yml -f docker-compose.demo.yml exec db psql -U postgres -c "select external_id, unit, sampling_interval_s from sensor where external_id like 'fac%';"

# Growth: run now, again after 5 and 10 minutes; good result: count rises about 5 per 3 s (one per sensor per tick)
docker compose --env-file .env.demo -f docker-compose.yml -f docker-compose.demo.yml exec db psql -U postgres -c "select count(*), min(ts_event), max(ts_event) from telemetry_sample;"

# Per-sensor counts and duplicates; good result: equal counts, zero duplicate rows
docker compose --env-file .env.demo -f docker-compose.yml -f docker-compose.demo.yml exec db psql -U postgres -c "select sensor_id, count(*) from telemetry_sample group by 1 order by 1;"
docker compose --env-file .env.demo -f docker-compose.yml -f docker-compose.demo.yml exec db psql -U postgres -c "select sensor_id, stream_id, ts_event, count(*) from telemetry_sample group by 1,2,3 having count(*) > 1;"

# Restart check: restart the API, wait 30 s, rerun the growth query; good result: count keeps rising, no error
docker compose --env-file .env.demo -f docker-compose.yml -f docker-compose.demo.yml restart api
```
(Database user, database name and the sensor table name are assumed from the compose files; adjust if they differ.) Also open `/telemetry` in the UI, and use the G-HIST runbook (`docs/frontend/contracts/G-HIST.md`) for the `samples` / `gaps` curl calls.
