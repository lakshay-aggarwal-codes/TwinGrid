# Model Card: Thermal Forecaster (LSTM)

**Status in the registry: `promoted`, under a named compatibility waiver, with no evaluation record.** Everything below is a
result on simulator-generated data. Machine-checked numbers are the `EVIDENCE` lines at the bottom; nothing else in this card
is a measurement.

## Intended use
Forecasts one number: the server outlet temperature (`server_outlet_temp_C`) 30 minutes ahead (`horizon` 6 steps of 5 min)
from the last hour (`seq_len` 12 steps) of sensor history. Used by the dashboard's forecast display; not used for
safety-critical control decisions (cooling control acts on current state, not on this forecast).

## Training data and split
`sensor_data.csv`, 90 days at 5-minute cadence generated by `src.data_generator` (itself driven by `DigitalTwin`'s physics),
not measurements from a facility. Chronological 80/20 split: the first 80% of rows train, the last 20% are the held-out test.
The file is not shipped in this repository copy, so the numbers below cannot be re-run from the repo alone; the registry
records the file's SHA-256.

## Results (held-out last 20%, simulator data)
- RMSE 0.523 °C and MAE 0.421 °C for the 30-minute-ahead outlet temperature.
- These are errors in the target's own units (the target is not rescaled before scoring).
- One training run. The registry records no seed for it, so there is no spread or confidence interval.

## Negative and unevaluated results
- **No baseline result for this model.** `scripts/forecast_baselines.py` (Task 11) computes a persistence ("same as now"), a 24-hour
  seasonal-naive and a train-mean forecast on the forecaster's own split, but it has not been run on the file this model was scored on:
  that file is not in this repository and the current data generator does not reproduce it (the registry records physics `legacy-0`).
  So there is no evidence that 0.523 °C is better than doing nothing. Do not describe this model as accurate or as an improvement.
- **The evaluation protocol is not strictly out-of-sample (Task 11 audit, `docs/tasks/Task11_REPORT.md`).** The split leaves no gap:
  the first 17 test windows read rows that the last train windows also read as inputs or targets. The 3-sigma outlier filter is
  computed on the whole file before the split, drops rows (so some windows span a time gap) and can remove labelled anomaly rows,
  so the score mostly describes non-anomalous dynamics. The script reports each of these for a given file; none has been measured
  on this model's own file. `DataPipeline(purge_gap=17)` removes the boundary overlap; this model was not trained that way.
- **No evaluation record.** The registry entry has no `evaluation_ref`, and it still carries the waiver
  `legacy-0-physics-until-T26`: it was trained under physics `legacy-0` whose parameters were not recorded, and no re-validation
  under the current physics is on file in the registry.
- The test rows come from the same generator and physics as the training rows, so the score cannot show behaviour on a real
  facility or on dynamics the simulator does not produce.

## Known limitations
- Trained entirely on synthetic data generated by the same physics model the rest of the system uses — metrics measure how well
  the LSTM fits `DigitalTwin`'s own simulated thermal dynamics, not real hardware behavior. See
  `docs/model_cards/LIMITATIONS.md` for the shared caveat.
- No held-out *drought* scenario in the forecaster's own training/eval split specifically — drought/water-stress dynamics are
  tested via the PPO optimizer's `compare_scenarios`, not this model's own eval.
- Single target, single horizon; no uncertainty estimate is produced.
