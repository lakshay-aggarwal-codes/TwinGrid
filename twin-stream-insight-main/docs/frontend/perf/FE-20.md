## How to produce the numbers

Prerequisites: backend under test with the seeded `E2E_VIEWER_*` account (see `e2e/helpers.ts`); the dev server
started **without** `VITE_DEMO_USERNAME`/`PASSWORD`; Chromium installed; IPv6 available for `npm run dev`
(`host: "::"`), as in FE-00.

```bash
# 1. Everything except bundle size and the full soak (about 15 min). PERF_SOAK_MINUTES=2 makes the S1 test run as a
#    smoke test: it will then FAIL its validity check on purpose so a 2-minute number is never filed as S1.
PERF=1 PERF_RACKS=36 PERF_SOAK_MINUTES=2 PERF_WRITE_RESULTS=1 \
  E2E_VIEWER_USERNAME=... E2E_VIEWER_PASSWORD=... npx playwright test e2e/perf.spec.ts

# 2. The real S1 (30 min soak + heap snapshots).
PERF=1 PERF_RACKS=36 PERF_WRITE_RESULTS=1 PERF_HEAP_SNAPSHOT=1 \
  E2E_VIEWER_USERNAME=... E2E_VIEWER_PASSWORD=... npx playwright test e2e/perf.spec.ts -g "S1"

# 3. Bundle size (production build; the dev server is not representative). Same placeholder env as FE-00.
VITE_API_BASE_URL=https://api.example.invalid VITE_DEMO_USERNAME=x VITE_DEMO_PASSWORD=x npm run build
PERF=1 npx playwright test e2e/perf.spec.ts -g "initial JS"
```

`PERF_WRITE_RESULTS=1` writes one JSON per scenario to `docs/frontend/perf/results/`. Without `PERF=1` the file does
nothing, so `npm run test:e2e` is unaffected. Traces: Playwright's `trace: "retain-on-failure"` applies as configured;
heap snapshots come from `PERF_HEAP_SNAPSHOT=1`. Chrome performance profiles and React Profiler captures are manual
(open the dev server, record while running the scenario) and belong beside the results.

Scenario validity is enforced, not assumed. The S1 test fails (after saving its numbers) unless `PERF_RACKS=36` is
attested, the observed median gap between frames is 2.5-3.5 s, the soak is at least 30 minutes, and the feed is live at
the end.

### Reading the render-count result (budget 1)

For each feed tick the result lists every component that performed work, by name. To judge it: take the fields that
changed in that frame (e.g. a rack temperature), list the components that read them through `useFeed` (and selectors),
and check that the rendered set is no larger. Components rendered outside that list are candidate breach findings.
Under React `StrictMode` the dev build double-invokes render functions but commits once, so the count is per commit.
This is a dev-build measurement; component names come from `displayName`/function name.

## Assumptions and limits (read before trusting a number)

1. **Initial JS baseline.** FE-00 recorded chunk sizes but not which chunks `/` loaded. The harness takes the largest
   reading: `three` 218.63 + `index` 196.87 + `Index` 170.36 = 585.86 kB gzip, so the ceiling is 644.45 kB. If `/`
   loaded fewer chunks at FE-00, the true ceiling is lower; rebuild the FE-00 tag to settle it.
2. **Parse budget is checked under the 4x throttle** because S1 runs throttled. That is the stricter reading. An
   unthrottled figure is not collected here.
3. **Heap** is the V8 used heap via CDP after two forced GCs; snapshots are optional.
4. **Subscriptions after unmount** is a page-level proxy (timers and sockets). A component-level "0 leaked after
   unmount" test would live in `src/**`, which this task does not allow. If the proxy shows growth, that becomes a
   finding naming the file, and FE-20b may add the unit test.
5. **Probes only observe.** They wrap `WebSocket`, `setInterval`, WebGL draw calls and the message handler, and read
   React commits. They add small overhead (the React hook only in its own test). They never alter, drop or delay data.
6. **S3** click-to-charts includes backend compute time; only the long-task count is frontend-attributable.
7. **S4** needs >= 5,000 stored samples in the window. If the backend returns fewer, the test records the count and
   skips: S4 is then **unmeasured**, not passed. Do not seed fake history to reach it (no fabricated data).
8. Facility interval and rack count come from the backend under test and are verified (interval) or attested (racks).
   A different count means a different scenario.

## Rules for FE-20b (only after a breach is listed)

- Touch only files named in a finding. Smallest change that removes the breach; re-run the same test and record
  before/after numbers here. One optimisation per commit so each can be reverted alone.
- Allowed techniques, only on a measured breach: `React.memo` / selector refinement; visible render throttling
  ("updates every N s") for a faster future feed; virtualised lists (alerts only above ~500 rows); backend
  aggregation; a worker only if parse cost breaches P95.
- **Not allowed:** client downsampling (it changes displayed values) unless the backend returns the full-resolution
  window and a contract-permitted aggregation is documented; silent frame dropping. Any throttle must be shown as such.
- A breach caused by backend payload size is **not** fixed in the frontend: raise it as a backend dependency.
